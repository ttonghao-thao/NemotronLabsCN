# ASR 3.5 中文接入后续工作计划

目标沿用[部署方案](deploy-asr35-zh.md)。保留原英文 RNNT 的权重、词表和解码策略。先恢复英文语音问答，再验证中文问题是否得到相关回答；分别记录助手文本和可听语音。中文 RNNT 转写质量作为旁路观测。

## 已有基线

现场使用同一条 `/s2s/what_is_your_name.wav`。原版和替换版均收到 362 个输入块、0 丢帧，完成 181 次 Triton 推理并发出 360 个音频块。原版 3.8 秒开始问候，随后转写并回答了问题；替换版没有可保存的用户或助手文本，用户报告输出 WAV 听不到声音。两份输出共用过目录，后续比较应按模型版本、样本和运行次数分目录。波形是否全零、内部 RNNT 是否全 blank、LLM 是否持续 PAD 均待测。

G1 对齐了 638 个同名同形状的参数或缓冲区。所报告 EN 0.083、ZH 0.0027 来自旧脚本的通道切片。部署文档中的 scenario C 可描述本次端到端结果；“潜空间正交”和“必须训练”的因果判断待以下实验验证。

## 1. 核对失败部署的模型产物

以失败部署实际挂载的目录为准，记录两次服务的镜像 ID、模型目录、代码挂载、启动参数和生效的 instructions。逐键比较 G2 的 `model.safetensors` 中去掉 `stt_model.perception.` 前缀的张量与 G3 的 `nemotron-voicechat/1/perception.safetensors`，核对键集合、形状、dtype 和值。对比两份配置的 perception 段，核实 `att_context_size=[56,0]`。按 G4 相同的 NeMo 版本实例化 perception，检查加载返回的 missing/unexpected keys，逐项解释差异，尤其关注 encoder 和 proj。同时核实 RNNT、投影及其余下游产物与原版的预期一致性。

G3 会跳过已存在的产物。发现差异时，在新的空目录重新导出，使用相同输入复测英文；若恢复，直接进入中英文验收。产物一致或修正后仍复现，再进入运行时对照。

## 2. 修正 G1，取得可解释的离线指标

在 [G1 脚本](../examples/speechlm2/verify_asr35_encoder_compatibility.py) 中先核实原始张量布局。对 `[B,D,T]`，每个样本取 `emb[0, :, :valid_len].T` 得到 `[T,D]`。核对新旧帧步长和时间起点，对共同有效帧逐帧沿特征维计算 cosine，并分别统计范数及非有限值。用旧 encoder 对自身的同一份确定性输出检查计算，再用已知逐帧结果的非方形张量检查轴向。重跑六条 G1 录音，保留原始报告和修正版，区分有声段和静音段。

此项可与产物核对并行。cosine 用于选取偏差较大的帧做检查；决定是否训练还需第 3 项的下游响应证据。

## 3. 在同一条英文样本上定位首次异常

固定镜像、提示词、输入、启动配置和采样设置。先用镜像自带的英文样本；按客户端 session ID 找到服务端 Triton sequence ID，各版本按输入帧对齐，排除 warmup。分别观察问候、用户说话和尾部静音。先收集现有日志，缺少的量再用临时诊断探针采集。

| 观测位置 | 记录 | 如何决定下一步 |
|---|---|---|
| 进入 Triton 的 PCM、preprocessor、encoder | 对齐后的 PCM、有效帧数、时间下标、NaN/Inf、语音与静音的能量、原始 `asr_emb` | 输入不一致先修输入；仅替换版出现非有限值、常量输出或错误帧下标时，先定位运行时感知路径。 |
| 旧 RNNT | 语音段 blank/nonblank、用户开始、EOU、转写增量 | 区分未检测到开口、未结束回合、仅旁路转写异常。原版问候先于客户端报告用户开口，仍需独立观察 LLM。 |
| adapter/proj 与 Nano 9B | 同帧投影后 `encoded_audio`、问候与回答时段的原生文本 token、轮次逻辑改写后的 BOS/EOS/PAD/正文、Triton `output_text` | 区分模型未生成正文、轮次逻辑改变了输出和服务端未分发文本。若只有轮次触发失败，用离线固定回合边界作一次归因对照，最终验收仍走正常 WebSocket。 |
| 音频输出 | 同帧是否有正文、返回 PCM 峰值与最响短窗 RMS、人工听感 | 有有效正文却无可听语音时，继续沿 EAR-TTS、codec 和 PCM 转换排查。 |

产出一份原版与替换版的同帧对照，标明第一次异常发生在何处、随后哪些输出受影响。两路可以分别失效。投影训练只影响 LLM 侧，旧 RNNT 直接读取投影前的 encoder 输出。

## 4. 仅在证据指向特征对齐时开展训练小试

先检查 ZH checkpoint 中 `modality_adapter` 的实际类型和可训练参数。如果它是 `IdentityConnector`，首轮可训练的是已有的 `proj`。冻结 encoder、LLM、TTS、旧 RNNT 和其他头，从 ZH checkpoint 初始化。核实参数白名单、梯度与单步更新，再安排训练。

仓库的 `NemotronVoiceChat.training_step()` 直接返回 `None`。优先验证 [DuplexSTTModel 的训练入口](../examples/speechlm2/s2s_duplex_stt_train.py)能否加载 VoiceChat 的 STT 子模块，使用对话回答标签计算 loss，并把更新的 perception 张量写回兼容 G3 的 checkpoint。先做一个 batch 的更新、导出、重新加载与 G4 英文回放。小试需确认只有预期张量变化，部署端读取了更新后的值。

正式训练数据使用中英文语音问题和对应助手回答，保留英文回归样本。按说话人及问题划分训练与验证，现有六条录音和镜像自带样本保留作回归。比较训练前后英文回答恢复情况和未参与训练的中文问题回答相关性，再决定是否扩大训练。若独立证据表明保留的 RNNT 始终无法触发正常回合，单列该限制；不要把投影侧的离线改善记为 G4 通过。

## 5. 回到原 G4 验收入口

用正常 WebSocket 会话测试自带英文、现有三条英文和三条中文录音。每个样本独立保留客户端日志、助手文本、可用的用户转写和返回 WAV。逐条记录是否听懂问题、是否给出对应回答、回答语言、是否有可听语音，以及问候与正文出现的时间。仅问候不能算回答。关键样本建议重复三次并记录每次结果。

先判定英文有无回归，再按部署方案判定中文语义是否通过；文本正确但音频静默或不可懂时，分别报告语义和语音结果。更新部署文档时，使用修正后的 G1 报告、实际模型版本和真实 G4 记录支持结论。
